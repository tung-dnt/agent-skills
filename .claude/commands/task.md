description: Build one task — claim, investigation and design note with a checkpoint after each step, your approval (catch-up summary + grill-me), then subagents build and review before commit and release
---

Work at **task scope**: one change that fits a focused session and touches no shared contract. Checklist items are the `## Checklist` checkboxes inside the task note.

## Before anything else

1. **Resolve the artifact root.** From the project, run `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" root`. If it reports `store=repo` and `configured=false`, propose a location using its notes, and write the config (`work-state.sh configure <storiesDir>`) only after the user confirms; with `store=vault` there is nothing to propose. `[stories-dir]` and `[epics-dir]` below mean the resolved `stories_dir` and `epics_dir` (absolute paths, possibly inside an Obsidian vault); their repo-store defaults are `docs/stories` and `docs/epics`. Change task state only through `work-state.sh` commands (`new-task`, `field`, `set`, `log`, `claim`, `approve`), never by editing frontmatter by hand. You still write the body sections (the task description above `## Design`, `## Design`, `## Summary`, and `## Checklist` ticks) with the file tools, at the path `work-state.sh path [story-id] [task-id]` prints.
2. **Read the input.** `$ARGUMENTS` may be free text, a slug, or a tracker key or URL. If it's a tracker item and a tracker tool is available, fetch its summary, description, type, parent, and children as input. The item's type is a hint, never the decider. Without a tracker, the repository's files are the tracker.
3. **Check the scope** against the signals in the "Scopes and Commands" section of the agent-skills work-artifacts reference (`references/work-artifacts.md` in the plugin). If the request belongs to a different scope, say so in one or two sentences with the evidence, recommend the right command, and continue only if the user confirms.

## Choose the task

- **`[story-id]/[task-id]`:** that task. Run `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" phase [story-id]`. If the story isn't at phase `build`, recommend `/story [story-id]` instead.
- **`[story-id]`:** the next claimable task: `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" next [story-id]`. Exit 4 means nothing is claimable; say why (all done, claimed, or waiting on dependencies) and stop.
- **A description with no story:** if the scope check says it's task-sized and touches no shared contract, create a one-task story: `work-state.sh init-story [story-id] "[title]"` (with `[story-id]` a short slug), then write `[stories-dir]/[story-id]/spec.md` (a few lines of goal and acceptance criteria) and `[stories-dir]/[story-id]/plan.md`, then `work-state.sh new-task [story-id] "T01 [title]"`, and write the task description into the note at the path it prints, above `## Design`. Never hand-write the task's frontmatter. In the repo store, commit the story's files; the vault store isn't in git. Otherwise recommend `/story`.

## Steps

**Stop at every checkpoint.** By default the user sees and confirms the work as it's produced: the investigation result, then each design step, then the whole design at the gate (`references/approval-gate.md` in the plugin, "Step Checkpoints"). Never run several steps and show only the final note. **The design gate is never skipped.** "Just build it", "don't stop", or "no questions" skips the step checkpoints and drafts the note in one pass; the gate still runs once, then there are no further stops. **Existing work gets the gate too:** if code or commits already exist for this task and `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" approved [story-id] [task-id]` doesn't exit 0 (for example, work from an earlier session), write a design note describing what was built and what should change, then run step 5 on it before any review, push, PR, merge, or tracker comment.

You are the orchestrator. Only you talk to the user; subagents investigate, design, build, and review, and each returns a report of 15 lines or fewer (`references/model-routing.md`). Read their reports, not their diffs, so this context stays small. **Every subagent prompt you write ends with the subagent command rules** (`references/model-routing.md` in the plugin): one plain command per shell call, with no scripts, variables, `$(…)`, or `&&` / `;` chains; the file tools for file work; no recursive deletes; and no `git push`, `ssh`, `docker run`, `docker exec`, `psql`, `kubectl`, `terraform`, or `publish`. For those it reports `needs-command`, and you run the command in this session. This keeps subagents from stopping the user with permission prompts.

1. **Claim.** Unless you claimed this task earlier in this conversation, or the user just adopted it through /resume, run `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" claim [story-id] [task-id] [work-branch]`. Exit 3 means another session holds it: choose another task or stop. Exit 5 means the claim couldn't be published: stop and report. `claim` itself sets the task to `in-progress` and records the work branch; when the work branch has no checkout yet (repo store), it prints a `set [story-id] [task-id] in-progress` command instead, to run from the new worktree. For a worktree per task, create the worktree only after the claim succeeds.
2. **Context.** Run `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" brief [story-id] [task-id]`. That is the whole context the subagents need; pass them paths, not content.
3. **Investigate** (bugs and unknown causes only). Spawn a read-only `Explore` subagent on the fast tier (`model: haiku`), or `sonnet` when reproducing needs a browser or running the app. It separates the observed symptom from the inferred cause, ranks hypotheses by evidence, and reports the one credible mechanism or the exact blocker. It never edits. **Checkpoint:** show the root cause, or the ranked hypotheses, with their evidence in 15 lines or fewer, and ask "Is this the right cause to design against?" Don't design until the user confirms. If they don't, investigate again with their input.
4. **Write the design note, one step at a time.** If the task note's `## Design` is empty, follow agent-skills:low-level-design in this thread. After each of its steps 1–6, stop at a checkpoint: show `Step N/6 — <name>` and what the step produced, ask about any decision it raised as a decision brief (the approach, for a bug or when more than one approach is plausible, comes at step 1), otherwise ask "Continue to step N+1?", and wait. Write each confirmed step into `## Design`, and add a log line with `work-state.sh log [story-id] [task-id] "text"`. You write the steps because a subagent can't stop to ask. When steps need a lot of reading (several files, unfamiliar code), first spawn a read-only `Explore` subagent (`model: haiku`) that returns the facts: contract ids, code paths, existing patterns. In one-pass mode ("don't stop"), a balanced-tier subagent (`model: sonnet`) may draft the whole note instead, given the story id, task id, and investigation report. If the note needs a change to a shared contract, stop: that belongs to `/story [story-id]`.
5. **Approval gate** (`references/approval-gate.md` in the plugin), in this thread:
   - write the catch-up summary into the task note's `## Summary` and show it (Business context · Proposed fix fit · Root cause for bugs · Recommendation · Open decisions), then **print the `## Design` note verbatim** below it, so the user approves the design itself
   - run agent-skills:grill-me over the decisions still open; never re-ask what a checkpoint settled. If the checkpoints didn't already settle it, for a bug, or when more than one approach is plausible, the first round includes the **approach question** as a decision brief: an options table (how it works, pros, cons and risks, effort, reversibility), what it hinges on, and the condition that would change your pick. Every other decision question uses the same format. Always ask at least "Proceed with this design?"
   - wait for the user's explicit go-ahead. When an answer changes the design, update the note and the summary and ask again
   - record it: `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" approve [story-id] [task-id]`. **Nothing is built before this.**
6. **Build.** Run `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" approved [story-id] [task-id]` first. A non-zero exit means no approval, or the design changed since approval: go back to step 5. Then spawn the `agent-skills:task-builder` subagent with the story id, task id, checkout or worktree path, the `work-state.sh` path, and the test command. If it reports `blocked`, put the named decision to the user through the gate, then send the builder back. If it reports `needs-command` (a container, database, push, or other command that always asks for permission), run that exact command yourself in this session, then send the builder back with the output. If it fails twice, run it once more on the main thread's model with a summary of both failures. If it still fails, stop and ask.
7. **Review.** Spawn `agent-skills:code-reviewer` on the task's diff, checking it against the approved note. Also spawn `agent-skills:security-auditor` when the task touches authentication, permissions, payments, secrets, or personal data; launch both back-to-back. Send Critical and Important findings to a new builder run.
8. **Finish.** Check that the task note says `done` (the builder ran `work-state.sh set [story-id] [task-id] done`) with a `## Log` line, and that the commit holds only this task's paths. In the repo store, commit the task note with the code: `git commit -- <task note> <code paths>`. In the vault store the note isn't in git, so commit the code paths only. Release the lock with `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" release [story-id] [task-id]` once `done` is on the base branch: right away if the commit is on the base branch, otherwise after the work branch is merged. A lock released before the merge lets another session take the task again. If you stop early for any reason, still write a log line saying what's done and what's next.
9. **Report** in a few lines: what changed, the evidence (tests, commit), and the next command: `/task [story-id]` for the next task, or `/story [story-id]` when the story reaches phase `done`.

Without subagents (another host), do steps 3, 4, 6, and 7 yourself in order. The approval gate stays the same.
