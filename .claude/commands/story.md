---
description: Take one story from requirements to an approved design and task plan, resuming at its current phase
---

Work at **story scope**: one user-facing capability that needs several tasks, or tasks that share a contract. Steps 1–3 each end at the approval gate (`references/approval-gate.md` in the plugin): write and show the catch-up summary, run agent-skills:grill-me rounds over the open decisions (always at least one question), and wait for the user's explicit go-ahead. Save the summary to `[stories-dir]/[story-id]/summary.md`, overwriting it at each gate. Never start the next step before the go-ahead. Each recorded go-ahead is also a boundary: before the next step, follow the boundary rule (`references/model-routing.md` in the plugin, "Fresh Orchestrator at Boundaries"): log what is next, name the exact next command, and recommend continuing in a new session. It is a recommendation: when the user answers to continue, start the next step in this session.

## Before anything else

1. **Resolve the artifact root.** From the project, run `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" root`. If it reports `store=repo` and `configured=false`, propose a location using its notes, and write the config (`work-state.sh configure <storiesDir>`) only after the user confirms; with `store=vault` there is nothing to propose. `[stories-dir]` and `[epics-dir]` below mean the resolved `stories_dir` and `epics_dir` (absolute paths, possibly inside an Obsidian vault); their repo-store defaults are `docs/stories` and `docs/epics`. Change task state only through `work-state.sh` commands (`init-story`, `new-task`, `field`, `set`, `log`, `claim`, `approve`, `approve-phase`), never by editing frontmatter by hand. If `root` flags the old `tasks/` layout, run `work-state.sh migrate` first.
2. **Read the input.** `$ARGUMENTS` may be free text, a slug, or a tracker key or URL. If it's a tracker item and a tracker tool is available, fetch its summary, description, type, parent, and children as input. The item's type is a hint, never the decider. Without a tracker, the repository's files are the tracker.
3. **Check the scope** against the signals in the "Scopes and Commands" section of the agent-skills work-artifacts reference (`references/work-artifacts.md` in the plugin). If the request belongs to a different scope, say so in one or two sentences with the evidence, recommend the right command, and continue only if the user confirms.

Pick the story id (a tracker key in lowercase, or a kebab-case slug), then run `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" phase [story-id]` and **start at the step that phase names**. Never redo an approved step unless the user asks. A phase advances only on the approval its gate recorded, so a spec that an epic left as a stub starts at step 1. If `phase` also prints `approvals=missing run: …`, the story was planned before approvals were recorded: show that line to the user, and run its command only if they confirm the earlier gates passed. Never run it to skip a gate.

**Every subagent prompt you write ends with the subagent command rules** (`references/model-routing.md` in the plugin): one plain command per shell call, with no scripts, variables, `$(…)`, or `&&` / `;` chains; the file tools for file work; no recursive deletes; and no `git push`, `ssh`, `docker run`, `docker exec`, `psql`, `kubectl`, `terraform`, or `publish`. For those it reports `needs-command`, and you run the command in this session. This keeps subagents from stopping the user with permission prompts.

## Steps

1. **Spec** (phase `none` or `spec`). Create the story's project note: `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" init-story [story-id] "[title]" [epic-id]`, passing the epic id only when the story belongs to an epic (it records the link). Invoke agent-skills:spec-driven-development and write `[stories-dir]/[story-id]/spec.md` with numbered functional requirements (`FR1`…) whose acceptance criteria can be tested, and non-functional requirements (`NFR1`…) as targets, drawing on `CONSTRAINTS.md` when it exists. When the story belongs to an epic, don't restate the epic. After the gate, record the go-ahead: `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" approve-phase [story-id] spec`.
2. **Design** (phase `design`). Invoke agent-skills:high-level-design and build the spec's `## Design` section one step at a time, with a step checkpoint after each of its steps 1–11 (show `Step N/11 — <name>` and the section, ask any decision as a decision brief or else "Continue?", and wait; skip the checkpoints only if the user asked for one pass). It covers: scope and out of scope, components, flows labelled sync/async, data ownership, how each NFR is met and verified, security, rollout, and shared contracts with ids (`C1`…) and concrete examples. When the story belongs to an epic, read the epic's `## Architecture` first and cite its `E` contracts instead of restating them. Compare at least two options for decisions that are hard to reverse and record ADRs. Run the fresh-context critique it calls for, then the approval gate, and record the go-ahead: `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" approve-phase [story-id] design`. Whether a small story needs a design at all is the user's call, put as a decision brief; on a skip, write no `## Design` and run the same command, which records the skip.
3. **Plan** (phase `plan`). Invoke agent-skills:planning-and-task-breakdown: write `[stories-dir]/[story-id]/plan.md` (a task index with dependencies and design refs; never status), then create each task with `work-state.sh new-task [story-id] "T01 [title]" [dependency-task-id…]` and record its contract refs with `work-state.sh field [story-id] [task-id] design_refs "C1, C2"` (`C` ids from this story's design, `E` ids from its epic's architecture). Write each task's description above `## Design` in its note, at the path `work-state.sh path [story-id] [task-id]` prints. Never hand-write the task frontmatter. Pass the approval gate once the task notes exist, then record the go-ahead: `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" approve-phase [story-id] plan` (it covers the plan and the task ids, so a task added later voids it, and a re-plan runs this gate again). In the repo store, commit the spec, plan, task notes, and the story's project note (it holds the approvals) so every worktree and machine can see them; the vault store isn't in git.
4. **Hand off** (phase `build` or `done`). Show `bash "${CLAUDE_PLUGIN_ROOT}/hooks/work-state.sh" status [story-id]` and end with the exact next command: `/build [story-id]` to build the story's tasks as a pipeline (you still review every task's design, and a task's builder starts while you review the next design), `/task [story-id]` to build one task, or `/build auto` to build all of them in one approved pass. When this hand-off follows the plan gate in this session, it is that gate's boundary: log and recommend as the boundary rule says. At phase `done`, recommend a whole-story review with agent-skills:code-review-and-quality, then agent-skills:shipping-and-launch.
