description: Implement a story's tasks — each task's builder starts as soon as its design is approved, while you review the next. Add "auto" to run the whole plan in one approved pass.
---

Invoke the agent-skills:incremental-implementation skill alongside agent-skills:test-driven-development.

**Resolve the artifact root first.** From the project, run `work_state root`. If it reports `store=repo` and `configured=false`, propose a location using its notes and write the config (`work_state configure <storiesDir>`) only after the user confirms; with `store=vault` there is nothing to propose. `[stories-dir]` below means the resolved `stories_dir` (an absolute path, possibly inside an Obsidian vault); its default in the repo store is `docs/stories`. Change task state only through `work_state` commands, never by editing a task note's frontmatter by hand.

## Modes

- **`/build [story-id]`** — a pipeline, the default for a story with several tasks: draft every task's design in parallel, walk you through each design in plan order, and start a task's builder the moment its design is approved, so builds run while you review the next design.
- **`/build [story-id]/[task-id]`** — claim that task and run the `/task` flow on it, including its approval gate, then stop. A story with one task left, a legacy plan, or tasks kept in an external tracker takes this flow too.
- **`/build auto`** — generate the plan if needed, draft every design note, pass one approval gate over all of it, then implement *every* task without stopping between them.

`$ARGUMENTS` selects the mode. Treat `auto` (canonical) or `all` as autonomous mode, and `[story-id]/[task-id]` as the single-task flow. Anything else (or empty) names a story, or defaults to the only story with unfinished tasks (ask which if there are several): with two or more unclaimed `todo` tasks it runs the pipeline, otherwise the single-task flow. Note: autonomous mode is not faster *per task* — it runs the same test-driven loop — it only removes the human stepping *between* tasks. The pipeline keeps every task's own design review and removes the waiting instead: design reviews and builds overlap.

## One task

Pick and claim a task. Other sessions may be building the same plan, so claim before you start (`references/work-artifacts.md` in the plugin describes the protocol):

- **Continue your own claim first:** if you claimed a task earlier in this conversation and it isn't done, or the user just adopted one through /resume, continue it and skip picking and claiming. Never take over another claim on your own: a claim you didn't make here may belong to a live session, even when its work branch is this checkout.
- **Find the plan:** `[stories-dir]/[story-id]/plan.md`. If several stories have unfinished tasks, ask which one. If only a legacy `tasks/plan.md` exists, build from it in this session alone; it is not safe for parallel sessions. If `root` flags the old `tasks/` layout, run `work_state migrate` first.
- **Pick:** bring the base branch up to date (`git pull --ff-only`), then run `work_state next [story-id]` (skip this when `$ARGUMENTS` names `[story-id]/[task-id]`). It prints the first unclaimed `todo` task whose dependencies are done; exit 4 means nothing is claimable, so stop and say so.
- **Claim:** run `work_state claim [story-id] [task-id] [work-branch]`. The work branch defaults to the current branch; for a worktree per task, name a new one. `claim` itself sets the task to `in-progress` and records the work branch; when the work branch has no checkout yet (repo store), it prints a `set [story-id] [task-id] in-progress` command instead, to run from the new worktree. Exit 3 means another session won the race, so pick again. Exit 5 means the claim couldn't be published, so stop and report. Only after the claim succeeds, for a worktree per task, run `git worktree add -b [work-branch] ../[repo]-[task-id]` and work there. A claim is yours only if you made it in this conversation; treat any other claim, even one whose work branch is this checkout, as belonging to another session.

Then follow the `/task` flow from its step 2 for the claimed task: context → investigation (bugs) with its checkpoint → design note with one checkpoint after its first step → **approval gate** (catch-up summary, agent-skills:grill-me, explicit go-ahead) → `agent-skills:task-builder` subagent → review subagents → finish and release → a short report. Nothing is built before the go-ahead.

## Pipeline: a story's tasks (`/build [story-id]`)

Designing and building need not alternate. Each task still passes its own design review (one step checkpoint, the approval gate, `approve`), but its builder starts the moment its design is approved and runs in the background while you review the next design, so **design reviews and builds overlap**. It is not `/build auto`, which passes one gate over every design, and it is not `/task` repeated, where each build holds up the next review.

1. **Require phase `build`.** Run `work_state phase [story-id]`: any other phase means the plan's gate hasn't passed, so stop and send the user to `/story [story-id]`. If it also prints `approvals=missing run: …`, the story predates recorded approvals: ask the user, and run that command only if they confirm the earlier gates passed. Check the baseline as `/build auto` step 2 does. A claim this conversation didn't make belongs to another session: leave it to `/resume`.
2. **Draft every design in parallel.** For every `todo` task whose `## Design` is empty, draft the design note first: one balanced-tier (`model: sonnet`) subagent per task following agent-skills:low-level-design, launched back-to-back, each writing only its own task note (the path from `work_state path [story-id] [task-id]`), and each prompt ending with the subagent command rules (`references/model-routing.md` in the plugin). A draft is a proposal: it approves nothing, and a subagent never talks to the user.
3. **Walk the designs in plan order, in this thread.** For each unclaimed `todo` task without a valid approval (`approved` exits non-zero):
   - **One checkpoint.** Run the single `low-level-design` step checkpoint (`references/approval-gate.md` in the plugin, "Step Checkpoints"), on the draft: show its step 1 facts and approach, plus any decision the draft raised as a decision brief, otherwise "Continue to the gate?"; the rest of the draft is shown at the gate. The user confirms or edits it; write each edit into `## Design` and log it with `work_state log [story-id] [task-id] "text"`. The Jev shadow check runs at each checkpoint, as that reference describes. A bug or unknown cause starts with the investigation checkpoint of `/task` step 3. A design that needs a shared contract changed stops here: that belongs to `/story [story-id]`. A design the user postpones leaves its task `todo` and unapproved: go on to the next one, and name it in the final summary.
   - **Gate.** Then the approval gate on the whole note: show the catch-up summary from the task note's `## Summary` and the `## Design` note verbatim in chat, run agent-skills:grill-me over what is still open, then ask "Proceed with this design?" (in omp, use the `ask` dialog without entering plan mode; `references/approval-gate.md` in the plugin, "Confirmation"). After the explicit go-ahead run `work_state approve [story-id] [task-id]`. In the repo store, commit the task note (`git commit -- <task note>`) at once: a worktree starts from HEAD and would not see the approval. The vault store isn't in git.
   - **Slice gates on a large story.** When the story has more than about five tasks or tasks in several repos, walk repo-sized slices instead of single tasks (`references/approval-gate.md` in the plugin, "Confirmation"): no step checkpoints; show the slice's combined summary and every task's `## Design` verbatim; ask once, "Proceed with this slice?"; after the go-ahead run `approve` for each task in the slice, and commit their notes in the repo store.
   - **Start builders.** After every approval, and whenever a builder finishes, run `work_state ready [story-id]`. It prints the tasks that can start together, one `story/task` per line in plan order: approved, dependencies done, and no file in common with a running task or with a task printed above it (lockfiles and generated outputs count; `references/work-artifacts.md` in the plugin has the rules). A `skipped:` line on stderr names a task it held back for a shared file; a later `ready` lists it once the other task is merged and released. Count the builders already running and take tasks from the top of the list up to the **wave cap**: 3, or the number the user asked for, never more than 5. For each one, run `claim [story-id] [task-id] task/[story-id]/[task-id]`, and only after the claim succeeds `git worktree add -b task/[story-id]/[task-id] ../[repo]-[task-id]`. Exit 3 means another session won, so skip the task. Exit 5 means the claim couldn't be published, so stop and report. Then spawn one `agent-skills:task-builder` subagent per claimed task **in the background, and do not wait for it**: pass paths, not content (the story id, the task id, the worktree path, and the test command), and end the prompt with the subagent command rules. Go on to the next design.
4. **Finish each task as its builder reports.** Take a report when the current checkpoint or gate exchange ends, never in the middle of one. Review, Escalate, Commands only you run, and Integrate are as in `/build auto` step 5: `agent-skills:code-reviewer`, and `agent-skills:security-auditor` when the task touches authentication, permissions, payments, secrets, or personal data, both started in the background so the walk isn't held up; Critical and Important findings go back to a builder; when a review passes, `set … done` and commit the task note in that worktree (repo store), then merge `--no-ff`, `release` the claim, remove the worktree, delete the work branch, and run `ready` again. A merge conflict means stop and ask.
5. **Stop and ask the user** when `/build auto` step 6 says to.
6. A wave is complete when builders have run and the pipeline goes idle: every builder started since the last boundary has reported and its task is merged and released, no builder is running, and `ready` exits 4. That is a boundary: follow the boundary rule (`references/model-routing.md` in the plugin, "Fresh Orchestrator at Boundaries"), with `/build [story-id]` as the next command. It resumes by drafting only empty designs and walking only designs without a valid approval. When no design is left to walk either, summarize as `/build auto` step 7 does, and name the tasks left unapproved, blocked, or waiting.

Without background subagents, work one task at a time: approve, build, review, merge, then walk the next design.

## Autonomous: the whole plan (`/build auto`)

Use this once a spec exists and you want to collapse plan + build into one run. It removes the manual stepping between tasks — **not** the verification. Every task still earns a passing test and its own commit.

1. **Require a spec.** Look only for a spec at a known path: `[stories-dir]/[story-id]/spec.md`, `SPEC.md` at the repo root, `docs/SPEC.md`, or a file under `spec/`. A README or arbitrary doc does **not** count. If none exists, stop and tell the user to run `/spec` first — do not invent requirements. For a story's spec, also run `work_state phase [story-id]`: phase `spec` or `design` means its gates haven't passed, so stop and send the user to `/story [story-id]`. If it also prints `approvals=missing run: …`, the story predates recorded approvals: ask the user, and run that command only if they confirm the earlier gates passed.
2. **Establish a clean baseline.** Run `git status --porcelain`. If there are uncommitted changes outside the expected planning artifacts (the story's files under `[stories-dir]/[story-id]/`, `SPEC.md`, `docs/SPEC.md`, `spec/*`, or a legacy `tasks/plan.md` / `tasks/todo.md`), stop and ask the user to commit, stash, or confirm how to handle them. Autonomous per-task commits must not absorb unrelated local work, or the clean-rollback guarantee breaks.
3. **Plan if needed.** If the story has no `[stories-dir]/[story-id]/plan.md`, invoke agent-skills:planning-and-task-breakdown to generate it and its task notes.
4. **One approval gate for the whole run.** This is batch mode, so there are no step checkpoints (`references/approval-gate.md` in the plugin). For every `todo` task whose `## Design` is empty, draft the design note first: one balanced-tier (`model: sonnet`) subagent per task following agent-skills:low-level-design, launched back-to-back, each writing only its own task note (the path from `work_state path [story-id] [task-id]`). Then pass the approval gate (`references/approval-gate.md` in the plugin) once, over the plan **and** every design note: write `[stories-dir]/[story-id]/summary.md` and show it, run agent-skills:grill-me rounds over the open decisions (always at least "Proceed with all N tasks?"), and wait for an explicit go-ahead. Show every task's `## Design` note, and put every decision to the user as a decision brief (options table with pros, cons, effort, and reversibility; what it hinges on; when you'd choose differently), including the approach for any bug or task where more than one approach is plausible. A hedged reply is not a go-ahead. After the go-ahead, run `work_state approve-phase [story-id] plan`, then `work_state approve [story-id] [task-id]` for every task. This is the only human gate, and a request to "just build it" or "don't stop" doesn't remove it. After it, run autonomously, and bring any decision a builder reports as `blocked` back to the user. In the repo store, whether or not you generated the plan, commit `[stories-dir]/[story-id]/` (the plan, the task notes with their designs and approvals, the project note with the plan approval, `summary.md`) as a single preparatory commit now, if anything changed, before step 5 claims a task or creates a worktree. A worktree starts from HEAD, so uncommitted designs and approvals would be invisible there and the task would go back to the gate; the commit also keeps them out of the first task's commit. In the vault store the notes aren't in git, so there is nothing to commit.
5. **Execute in waves, as the orchestrator.** Delegate building to subagents and keep only their short reports in this context (`references/model-routing.md` in the plugin). **Every subagent prompt you write ends with the subagent command rules** (`references/model-routing.md` in the plugin): one plain command per shell call, with no scripts, variables, `$(…)`, or `&&` / `;` chains; the file tools for file work; no recursive deletes; and no `git push`, `ssh`, `docker run`, `docker exec`, `psql`, `kubectl`, `terraform`, or `publish`. For those it reports `needs-command`, and you run the command in this session. This keeps subagents from stopping the user with permission prompts. Repeat until `work_state ready [story-id]` exits 4 and no builder is running:
   - **Fill the wave:** run `work_state ready [story-id]`. It prints the tasks that can start together, one `story/task` per line in plan order: approved, dependencies done, and no file in common with a running task or with a task printed above it (lockfiles and generated outputs count; `references/work-artifacts.md` in the plugin has the rules). Take up to 3 tasks, or the number the user asked for (never more than 5), counting builders still running. For each one, run `claim [story-id] [task-id] task/[story-id]/[task-id]`, and only after the claim succeeds run `git worktree add -b task/[story-id]/[task-id] ../[repo]-[task-id]`. Exit 3 means another session won, so skip it. Exit 5 means the claim couldn't be published, so stop and report. A `skipped:` line on stderr names a task `ready` held back for a shared file: it isn't lost, the next `ready` lists it once the other task is merged and released, so a short wave is expected.
   - **Delegate:** only tasks where `work_state approved [story-id] [task-id]` exits 0 get a builder. Anything else goes back to the gate. Spawn one `agent-skills:task-builder` subagent per claimed task, and launch them back-to-back, in one turn where possible, without waiting for results, so they run concurrently. Pass paths, not content: the story id, the task id, the worktree path, and the test command. The builder records progress with `work_state log` and `set … review` when its acceptance criteria pass; it never sets `done`, and it never edits the frontmatter itself.
   - **Review:** for each `review` report, spawn `agent-skills:code-reviewer` on that worktree's diff against the base branch. Also spawn `agent-skills:security-auditor` when the task touches authentication, permissions, payments, secrets, or personal data. Launch a wave's reviews the same way. Send Critical and Important findings back to a builder as a retry: first run `work_state set [story-id] [task-id] in-progress`, and the builder returns the task to `review` when its fixes pass. When a review passes, with no Critical or Important finding left, run `work_state set [story-id] [task-id] done` and, in the repo store, commit the task note in that worktree (`git commit -- <task note>`), so `done` merges with the work.
   - **Escalate:** a task that fails twice is re-run once with a builder on the main thread's model, given a summary of both failures. If it still fails, or a builder reports `blocked`, stop and ask (step 6).
   - **Commands only you run:** a builder that reports `needs-command` gets it run by you, in this session, then goes back to work with the output. Builders never run permission-gated commands (push, ssh, containers, database shells, recursive deletes) themselves.
   - **Integrate:** merge each reviewed work branch into the base branch in this checkout (`git merge --no-ff task/[story-id]/[task-id]`), then `release` its claim, remove its worktree, and delete the merged work branch. A merge conflict means stop and ask. Merging is what lets `ready` see a finished dependency.

   Each task still ends as its own test-driven commit on its work branch, so any point is a clean rollback. Without subagents, run the same loop one task at a time in this session. A wave is complete when every builder it started has reported and its task is merged and released. That is a boundary: follow the boundary rule (`references/model-routing.md` in the plugin, "Fresh Orchestrator at Boundaries"). This run is unattended, so log what is next, put the next command (`/build auto [story-id]` resumes) and the recommendation in the wave's status line, and carry on with the next wave.
6. **Stop and ask the user** (do not push through) when:
   - a test can't be made to pass or the build breaks without an obvious fix → follow agent-skills:debugging-and-error-recovery
   - the spec is ambiguous, or a task needs a decision the spec doesn't cover
   - a task is high-risk or irreversible — auth/permission changes, destructive data migrations, payments, deletions, deploys, anything touching secrets, **or anything you can't undo with `git revert`** → follow agent-skills:doubt-driven-development and get explicit sign-off before continuing

   After the user resolves a blocker, they re-invoke `/build auto` — it resumes from the next unclaimed `todo` task.
7. **Summarize at the end:** tasks completed, tests added, commits made, and anything skipped, flagged, or left for the user. Then apply the boundary rule once more: the next step is the whole-story review (`/review`), best started in a fresh session.

If any step fails, follow the agent-skills:debugging-and-error-recovery skill.
